# Object Storage Guidelines

These rules define MinIO and S3-compatible object storage usage.

## Ownership

- `src/packages/storage` owns S3-compatible client setup, object key generation, upload/download/delete helpers, and signed URL helpers.
- Domain packages call `src/packages/storage`; they do not instantiate S3 clients directly.
- Object metadata is persisted in PostgreSQL by the owning domain package.

## Buckets

Use a small, stable bucket set:

| Bucket | Purpose |
| --- | --- |
| `kb-source` | Original uploaded files and fetched URL source snapshots |
| `kb-derived` | Derived artifacts such as normalized text snapshots when persisted |
| `kb-temp` | Temporary objects awaiting cleanup |

Bucket names must be configurable for private deployments.

## Object Key Format

Object keys are generated by the server.

Recommended format:

```text
tenants/{tenantId}/knowledge-bases/{knowledgeBaseId}/documents/{documentId}/versions/{documentVersion}/{kind}/{filename}
```

Where `kind` is one of:

- `source`
- `normalized`
- `derived`
- `temp`

Rules:

- Never trust client-provided object keys.
- Include tenant and knowledge-base identifiers in keys.
- Use sanitized filenames only as the final display-oriented segment.
- Include a document version or source hash for objects that may be re-ingested.

## Upload Rules

Upload APIs must validate before object write:

- Actor has write access to the knowledge base.
- File size is within configured limit.
- MIME type is allowed.
- Extension is allowed as a secondary signal.
- Parser exists for the content type.

Production v1 allowed document uploads:

- PDF
- Markdown
- TXT

HTML is accepted through URL ingestion, not arbitrary HTML file upload, unless the API explicitly supports it.

## Metadata Persistence

Persist storage metadata in PostgreSQL:

- `tenantId`
- `knowledgeBaseId`
- `documentId`
- `documentVersion`
- `bucket`
- `objectKey`
- `originalFilename`
- `mimeType`
- `sizeBytes`
- `checksum`
- `createdBy`
- `createdAt`

Database metadata is the source of truth for authorization and lifecycle operations. Object storage alone is not a source of authorization truth.

## Downloads

Downloads must authorize against database metadata before reading object storage.

Rules:

- Admin can download tenant-owned source objects.
- Member can download only objects belonging to authorized knowledge bases.
- Failed authorization must not reveal whether the object key exists.
- Use streaming download for large objects.

## Signed URLs

Signed URLs are optional. If used:

- Generate only after authorization.
- Keep TTL short.
- Scope to a single object and method.
- Never expose provider credentials.
- Log signed URL creation metadata without the full signed URL query string.

## Temporary Objects

Temporary objects must:

- Use `kb-temp`.
- Include tenant id and a generated id in the key.
- Have a database record or cleanup marker.
- Be removed after successful promotion or after expiration.

Worker cleanup should delete expired temp objects and log counts, not object contents.

## Deletion

Prefer soft-delete metadata first, then async object cleanup.

Deletion process:

1. Check authorization.
2. Mark document/source as deleted or superseded.
3. Enqueue cleanup or run storage deletion in a controlled worker.
4. Record audit event.

Failed object deletion should be retryable and visible in operations logs.

## Security

Never log:

- Access keys.
- Secret keys.
- Full signed URLs.
- Raw object contents.

Object storage credentials must be loaded from validated configuration and redacted from config dumps and logs.
