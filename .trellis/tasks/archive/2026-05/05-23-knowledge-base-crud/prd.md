# knowledge-base-crud

## Goal

Implement end-to-end knowledge base create, read, and update functionality. The
feature must expose real backend APIs, add the `@kb/knowledge` service layer, and
connect the workspace UI to those APIs instead of the current knowledge-base
mock state. Delete is explicitly out of scope.

## Confirmed Requirements

- Implement a complete backend-to-frontend flow:
  - Backend API routes for knowledge base list, detail, create, and update.
  - `@kb/knowledge` service layer for validation, authorization, persistence,
    and member updates.
  - Frontend workspace integration using the real API for listing, creating,
    editing, and selecting members.
- Do not implement delete API routes, delete service methods, or delete UI.
- Do not create or switch git branches for this task. User confirmed on
  2026-05-23 that main branch changes were stashed and no new branch is needed.
- Frontend implementation must be done through a subagent to avoid polluting the
  main session context. The main session should coordinate the task, preserve
  requirements, and verify/merge results, but should not directly perform broad
  frontend edits.
- Knowledge base create form fields:
  - Name.
  - Description.
  - Members who can view the knowledge base.
- Knowledge base edit form fields:
  - Name.
  - Description.
  - Members who can view the knowledge base.
- Search must fuzzy match name and description.
- Member selection is optional. Empty member selection means only admins can
  view and manage the knowledge base until members are added later.
- Admins always can view and manage all knowledge bases.
- Members can view only knowledge bases they are explicitly authorized for via
  `knowledge_base_members`.
- Only admins can create knowledge bases, edit knowledge bases, and edit member
  assignments.
- Members can only view authorized knowledge bases and use related document and
  Q&A capabilities.
- Member picker behavior:
  - Show only current-tenant users with `role=member` and active tenant access.
  - Do not show admin users in the picker.
  - Persist only selected member users to `knowledge_base_members`.
  - Reuse the existing user list API as the picker data source.
  - Frontend searches member options with `filter=member` and `search`.
  - Do not add a dedicated member-options endpoint for this task.
- Knowledge base names must be unique within a tenant after trimming and
  case-insensitive comparison.
  - Create/update duplicate names return `409 CONFLICT`.
  - `slug` is generated by the service and is not exposed in UI.
- Knowledge base list query:
  - Use URL query state.
  - `search` fuzzy matches name and description.
  - `page` defaults to `1`.
  - `pageSize` defaults to `8` and is limited to `5`, `8`, or `12`.
  - `sort` defaults to recently updated and supports name sorting.
  - Response includes current user's visible knowledge bases, member summaries,
    and document counts.
  - Admin sees all tenant knowledge bases.
  - Member sees only authorized knowledge bases.
- Knowledge base detail query:
  - Implement `GET /api/knowledge-bases/:knowledgeBaseId`.
  - Use detail data when opening edit dialog so stale list data is not submitted.
  - Detail response must include currently selected member summaries so edit
    dialogs can preserve selected members even when the user list API is paged
    or filtered.
- API endpoints:
  - `GET /api/knowledge-bases`
  - `GET /api/knowledge-bases/:knowledgeBaseId`
  - `POST /api/knowledge-bases`
  - `PATCH /api/knowledge-bases/:knowledgeBaseId`

## Rate Limiting and Concurrency

- Backend enforcement is primary.
- Frontend duplicate-submit prevention is secondary.
- Knowledge-base APIs must use the existing `rateLimiter`.
- Authenticated requests are rate-limited by `tenant + actor`.
- Unauthenticated or invalid-session requests are rate-limited by IP.
- Rate-limit failures return `429 RATE_LIMITED`.
- Create/update service operations must use database transactions to update the
  knowledge base row and member rows atomically.
- Create/update must reject or normalize duplicate member IDs within the same
  request so the service never attempts duplicate member writes.
- Frontend submit buttons must be disabled while create/update mutations are
  pending.

## UX Requirements

- Workspace knowledge-base list should use real API data instead of mock state.
- Search, pagination, and sort state should be reflected in the URL.
- User confirmed on 2026-05-23 that the visible knowledge-base list should use
  sliding/infinite-scroll display instead of visible pagination and sort
  controls:
  - Keep the backend paginated list API unchanged.
  - The frontend loads page 1, then fetches and appends the next page when the
    user scrolls near the bottom of the knowledge-base list.
  - The workspace URL should keep `search` and selected `knowledgeBaseId`; do
    not reintroduce visible pagination, page-size, or sort controls.
  - The frontend may keep the backend default sort as recently updated
    internally, but should not expose a "recently updated" control or timestamp
    component in the workspace list.
- Admin users can open create and edit flows.
- Member users cannot create or edit and should only see authorized knowledge
  bases.
- Create/edit dialogs must show pending, validation, success, and API error
  states consistent with existing admin user management patterns.
- Member picker should make selected users clear and should support zero
  selected members.
- Delete affordances must not appear.

## Frontend Modification Scope

The current frontend implementation is mock-first and diverges from the backend
requirements. This task must update the frontend, not only add backend APIs.
Frontend edits in this section must be delegated to a subagent during
implementation.

- Replace knowledge-base data in `WorkspaceMvpPage` from `useMockStore()` with
  TanStack Query hooks backed by the new knowledge-base API.
- Add knowledge-base query/mutation hooks under the workspace or API feature
  area, following the existing user-management hook style.
- Keep shareable list state in URL query parameters:
  - `search`
  - `page`
  - `pageSize`
  - `sort`
  - selected `knowledgeBaseId`
- Move knowledge-base search from local mock filtering to server-side query
  parameters.
- Add pagination controls for the knowledge-base list because the backend list
  is paginated.
- Add a sort control for recently updated vs name sorting.
- Add an edit action for admins on the selected knowledge base.
- Replace the current create dialog, which only collects name/description, with
  a create/edit dialog that supports:
  - name
  - description
  - zero or more selected member users
  - pending disabled state
  - API validation/error state
  - success notice
- Member picker must reuse the existing user list API with `filter=member` and
  `search`, while relying on the knowledge-base detail response for already
  selected members.
- Do not use mock `MockVisibility` (`private`/`shared`) to render authorization.
  Authorization display must be derived from backend response data, such as
  member summaries/counts and the rule that admins always have access.
- Do not expose or edit backend `slug` or `visibility` fields in the UI.
- Preserve the workspace document/task/log summary layout where possible, but
  it must be driven by the selected real knowledge-base ID. If the existing
  mock document/task/log data cannot be safely reconciled with the real
  knowledge-base list in this task, show backend-compatible empty/loading states
  instead of mixing incompatible mock knowledge-base data into the real
  knowledge-base list.
- Upload/import buttons may remain present only if they can operate against the
  selected real knowledge-base ID without reintroducing mock knowledge-base
  state. Otherwise they should be disabled with clear copy until the document
  upload/import task provides the real integration.
- Remove knowledge-base create/update behavior from the mock store path for the
  workspace page. Existing unrelated mock features should not be refactored
  unless required by the workspace migration.
- Update `src/apps/web/src/copy/knowledge.ts` for create/edit/member/pagination
  copy and backend API error wording.
